## 四、結論

**總體判斷：⚠️ 勉強可用 — 無 DB locked、無寫入遺失，但 app.run() 在並發下把重型細表讀取排隊序列化，p95 飆到秒級，建議改 waitress**

- DB locked 總次數：**0**
- 請求失敗總數：**0**
- 寫入遺失：**0**
- 最慢操作：**detail_read(大表)**（最大 11397.9 ms）

### 根因（附數據佐證）

重型細表讀取 `/api/ie/<hid>/sheet`（讀 ie_sheet_data 大表）：
- 單線程基準：**90.7 ms**
- 20 並發下：平均 **7501.0 ms** / p95 **10693.5 ms** / 最大 **11397.9 ms**
- 並發/單線程倍率 ≈ **82.7×**（20 並發；倍率遠大於 1）

單次讀取只要 90.7 ms（DB 查詢不慢、索引有效），但 20 人同時開細表時平均要等 7501 ms、最後一個人等到 ~11398 ms。耗時隨並發數近乎線性放大（倍率 82.7× ≫ 1），代表 `app.run()`（Werkzeug 開發伺服器）**把請求排隊逐一處理、沒有真正並發服務**。DB locked=0、寫入遺失=0、失敗=0，**瓶頸不在 SQLite，而在前端伺服器序列化**。

### 必要改善

1. **改用 waitress（最關鍵）**：`pip install waitress` → `python -m waitress --host=0.0.0.0 --port=5000 --threads=8 app:app`（零改 app.py）。多線程同時服務多個讀取請求，重型細表 p95 可由 10693.5 ms 降回接近單線程的 90.7 ms 量級。
2. **細表大表前端分頁/虛擬捲動**：單一 sheet 一次回 12,000 cells，單次 90.7 ms 主要花在序列化大量 cell。已有索引 `idx_ie_sheet_data_hdr(header_id, sheet_name)`，DB 端無需加索引；建議前端按可視範圍分批載入，降低單次傳輸量。
3. **（次要）提高 SQLite busy_timeout**：`get_conn()` 用預設 5s timeout，本次未觸發 locked；切 waitress 後寫入並發升高，可預防性加 `PRAGMA busy_timeout=15000`。
