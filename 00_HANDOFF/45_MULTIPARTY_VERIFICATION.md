# 45｜上線前多方驗證機制（Multi-Party Verification Protocol）

> 建立 2026-07-15。起因：IE表/編制表/SmartPN 上線後仍有小 bug 被 Jim 一眼抓到——
> 根因是「驗的人＝做的人」，單一驗證者被自己的盲點騙（CSA 只驗一個單位、閘門搜字串、
> Code 改判定自證綠）。本機制用**角色對立 + 各自獨立 + 互相攻擊**取代單方自證。
> Status: ACTIVE。任何「要給 Jim 看／要上 ME129」的交付，都必須先過本機制。

---

## 一、為什麼單方驗證會失敗（已發生的實例）

| 失敗案例 | 根因 | 對應防線 |
|---|---|---|
| CSA 只驗 1 單位卻宣布 13 單位全綠 | 閘門只量到規格的一個實例 | 對規者：逐結構維度對帳 |
| 閘門搜「有沒有那個字串」就給綠 | 驗「存在」不驗「能用」 | 使用者：真點擊走流程 |
| Code 改判定標準自證死按鈕=0 | 建造者當自己的裁判 | 建造者不得改判定；破壞者獨立打 |
| splash 頁把 13 顆死鈕洗白 | 作弊從測試層搬到頁面層 | 破壞者：全新頁面零預備 |
| 匯入間歇失敗查不出 | 單發測不出並發 bug | 破壞者：並發/重試/壞資料 |
| 2026-07-15 更新鈕地雷（由 Jim 人工發現）| 13 支閘門全綠，卻**沒有一支攻擊「營運/發佈路徑」**——`/api/system/update` 直接 `git pull origin main` 後重啟，開發者一 push 半成品，現場誤按更新就拉到半成品 → 程式新/DB 舊 → 白畫面，且現場沒有回頭路 | 破壞者攻擊面永久擴充「營運/發佈路徑」＋ hub_ci 常設閘門14 `deploy_gate`（規則 R1/R2） |

共同點：**做的人和驗的人是同一個腦，盲點一致。** 解法＝引入立場對立的獨立驗證方。

## 二、四方角色（互相看不到彼此結論）

### 建造者（Builder）＝ Code
- 實作 + 自測 + 跑 hub_ci 全綠。
- **不得當自己的裁判**：hub_ci 綠只是「入場券」，不是「通過」。
- 不得修改任何閘門判定（改判定＝作弊，直接作廢）。

### 破壞者（Breaker）＝ 獨立 AI 視窗
立場：**這東西一定有 bug，我的工作是弄壞它。**
攻擊清單（每項都要試、附證據）：
1. 亂點：每個按鈕連點、空狀態點、快速切換
2. 並發：同時發 N 個相同請求（匯入/儲存/重算）
3. 壞資料：半截檔、空值、超大值、注入字串、全形、錯型別
4. 邊界：0 筆、1 筆、最大筆數、缺前置條件就執行下一步
5. 權限繞過：低權限帳號硬打高權限端點
6. 狀態殘留：做一半離開、回退、切月份/版本後原值是否殘留
7. **營運/發佈路徑（規則 R1，2026-07-15 定案，永久）**——每批 push 前必模擬：
   - 按更新鈕（各時點：開發中／push 後／中樞核可前／核可後）
   - 還原備份
   - 半新程式 + 舊 schema
   - 舊程式 + 新 schema
   - 更新中斷電重啟
   判定：**任何一項讓現場掛死或白畫面＝紅，擋 push。**
   自動化：hub_ci 常設閘門14 `deploy_gate`（規則 R2），與其他閘門同等地位，**缺跑＝整批不過**。
   由來：本項是 2026-07-15「更新鈕地雷」的永久修正——那顆地雷 13 支閘門全綠也擋不住，
   因為破壞者只攻「功能」沒攻「發佈」。功能對、發佈錯，現場一樣是停產。
輸出：**「我試了什麼 → 結果如何 → 這是不是 bug」**，不接受「我覺得還好」。

### 對規者（Spec-Auditor）＝ 獨立 AI 視窗
立場：**不符 Jim 的原始規格檔就是錯，我不看 Code 說什麼。**
- 只讀 Jim 的規格檔（28_BIANCHE_SPEC / 16_S02_TO_S17 / 27_WORKING_RULES）。
- 逐條、逐欄、逐結構維度對帳（所有單位/所有月份/所有角色/所有 EOLR，不是抽一個）。
- 覆蓋率必須量化：驗了幾個實例 / 規格要求幾個。
- 數字可追溯：畫面每一格能從來源算出，不是「有這個欄位」就算過。

### 使用者（User-Sim）＝ 獨立 AI 視窗
立場：**我是不看說明、會亂搞的工廠新人，走不通就是 bug。**
- 照真實工作流程從頭走到尾（匯入→勾選→計算→導出／申請→授權→交換）。
- 每一步斷言「畫面實際變化」，走到死路/空白/數字錯即記錄。
- 不用捷徑、不呼叫內部 API，只用真實點擊路徑（BFS）。

### 裁決者（Arbiter）＝ 中樞（Claude 本體）
- 收四方報告，用 **Jim 的真實 atlas.db** 獨立複跑閘門。
- **交叉比對**：破壞者說壞、建造者說好 → 以破壞者的可重現證據為準。
- **全票制**：四方全綠才放行；任一方紅 = 退回，不是多數決。
- 產出「哪些真的能用、哪些還不行」的覆蓋率報告，只有全綠才對 Jim 說「可以看」。

## 三、執行流程（每次交付強制）

```
Code 實作 → hub_ci 全綠(入場券)
   ↓
中樞派三份獨立任務(破壞者/對規者/使用者)——各自視窗，互不通氣
   ↓
三方各交「試了什麼+證據+紅/綠」
   ↓
中樞用 Jim 真庫複跑 + 交叉比對四方
   ↓
全綠 → 對 Jim 說「可以看」+覆蓋率報告
任一紅 → 自動生成退回令給 Code → 循環
```

**Jim 的角色：只搬運（貼任務、丟報告）+ 最終拍板。不當測試員、不當糾錯員。**

## 四、落地工具（讓機制可重複，不靠人肉）

1. `hub_ci.py`——建造者入場券（全閘門一鍵跑，真庫形狀）。
2. `spec_gate_*.py`——對規者的自動化底層（bianche/ie/smartpn/import/flow/bfs）。
3. `fresh_click_test.js` + `spec_gate_bfs.py`——使用者的真點擊底層。
4. **破壞者閘門（待建）** `breaker_gate.py`：自動化的並發/壞資料/權限/邊界攻擊套件，
   每個新端點自動納入攻擊面。
5. 三份「破壞者/對規者/使用者」的 AI 視窗 prompt 範本（見 §五）。

## 五、三方獨立驗證 prompt 範本（中樞每次交付前發出）

每份都要求：先讀 GitHub 最新碼 → 依角色立場攻擊/對帳/走流程 → 只輸出
「①我做了什麼 ②證據(數字/截圖/重現步驟) ③紅或綠 ④若紅，最小重現」。
不接受「我覺得」「應該沒問題」。三方收齊回中樞交叉比對。

（範本正文由中樞每次依當次交付內容填入具體攻擊面/規格條號/流程步驟。）

## 六、鐵則（寫入 27_WORKING_RULES）

1. **驗的人 ≠ 做的人**：Code 的自證只是入場券，必經破壞者/對規者/使用者三方獨立驗。
2. **全票制**：任一方紅即不上線，非多數決。
3. **證據制**：每方交「試了什麼+可重現證據」，不接受主觀判斷。
4. **閘門不得由被驗收方修改**：改判定＝作弊。
5. **上 ME129 前必過本機制**：中樞用 Jim 真庫複核全綠才放行。
